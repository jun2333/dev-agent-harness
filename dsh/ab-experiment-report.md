# A/B 实验报告：单会话自觉流 vs 编排流

> 日期：2026-08-18
> 目标项目：taskflow（~/Documents/Jun/code/taskflow，Next.js 14 + tRPC + Prisma + NextAuth v5）
> 测试功能：看板任务筛选（关键词/优先级/负责人，客户端纯函数过滤）
> 本报告为「编排器优先落地」的决策依据文档。

## 1. 实验设置

| 项 | Run A | Run B |
|---|---|---|
| 执行模型 | 单会话自觉流（harness.md 自驱动，上下文累积） | 编排流（每阶段独立干净子代理 + schema 门禁 + 人工门禁） |
| 分支 / 提交 | taskflow `ab/run-a` @ `3eaaea4` | taskflow `ab/run-b` @ `91cac07` |
| 任务 id | task-001 | task-002 |
| 基线 | 相同（`fe1b55e`：.harness→dsh-version + verify.config + .eslintrc 基建） | 相同 |
| 工作流 | feature（designing→task-planning→implementing→testing→reviewing→reflecting） | 同左 |
| 验证通道 | verify.js（配置命令全量执行，他证） | 同左 |

**注意**：实验 N=1、执行者为不同 agent 实例（相同模型、不同上下文/提示词），非受控变量实验；结论聚焦**结构性差异**，不用于量化模型能力。

## 2. 结果对比

| 维度 | Run A | Run B | 差异 |
|---|---|---|---|
| 阶段完成 | 6/6，0 返工 | 6/6，0 编排级返工（testing 阶段内自修复 2 条测试数据缺陷） | ≈ |
| 用户门禁 | 4 次确认全一次过 | 4 次确认全一次过 | ≈ |
| 确定性门禁 | gate-check 5 次全过 | gate-check 5 次全过 + 证据对账显式 PASS + JSON 摘要 schema 校验 | Run B 多一层数据级门禁 |
| 验证证据 | vitest 13 + lint | vitest 24 + lint | 都是 verify 通道、配置命令全量 |
| 审查发现 | 0C / 0W / 3S / 0P1 / 3P2 | 0C / **1W / 5S / 2P1** / 2P2 | **Run B 显著更严** |
| 复盘产出 | 3 经验 + 2 技能建议 | **6 经验 + 4 技能建议** | Run B 翻倍 |
| 编排器上下文 | —（单上下文累积全部阶段产物+知识库+代码） | 只持有各阶段 JSON 摘要与门禁结果 | **Run B 显著更轻** |

## 3. 关键发现

### 3.1 独立上下文审查更严（最重要的结论）

Run A 的审查由**实现者同一上下文**执行（自审），得出 0 Warning / 0 P1；
Run B 的审查由**干净上下文的独立子代理**执行，抓出 1 Warning + 2 P1（含 UI/UX 问题）。

结论：**同一上下文内的自我审查存在系统性锚定偏差**——实现者对"自己为什么这么写"的解释会覆盖对"这样写对不对"的判断。审查有效性主要来自**信息独立性**，而非审查指令的质量。

→ 编排流把 reviewing 阶段的独立性变成结构性保证（干净上下文），这是它相对单会话流最硬的价值。

### 3.2 复盘质量翻倍

Run B 沉淀 6 条经验 + 4 条技能建议（含 Prisma `include` 只接受关系字段的 ORM 语义级发现、参数化测试 fixture 碰撞），Run A 为 3 + 2。
新鲜上下文复盘不受实现惯性污染，想得更全。

### 3.3 编排器上下文显著更轻

Run B 编排器全程只处理 JSON 摘要、门禁结果与分支切换；阶段原始内容留在各子代理上下文。
Run A 把全部阶段产物 + 知识库 + 代码读进同一上下文。

→ **context-ledger、token 预算表、按需加载策略在编排模型下可退役**（"精准上下文"从管理变成构造）。

### 3.4 证据链在两个模型下都稳

两轮均走 verify 他证通道（命令只来自 knowledge/verify.config.json、gate 对账），无伪造、无跳过。
→ 证据链约束与执行模型无关，已由 v0.4 机械化为项目配置驱动。

## 4. 决策结论

1. **编排器（每阶段独立子代理 + schema 门禁 + 人工门禁）应作为 DSH 版本默认执行模型优先落地**——它同时改善审查独立性（P0 级可靠性问题）、复盘质量、上下文成本三个维度。
2. 单会话流保留为 CLI 目标的执行形态（hook 层最优），不作为 DSH 版本目标形态。
3. gate-check 在 DSH 中作为确定性复核保留（bash 直接复用），与编排器 schema 校验互补（前者查文件与证据，后者查子代理摘要）。
4. 后续实验建议：多任务样本（N≥3）验证审查独立性收益的稳定性；对比不同模型的独立审查效果（P1 双轨审查）。
