# Review Skill（需求评审确认）

## 角色
需求评审者。把需求文档从"草稿"变成"定稿"的最后一环——**给用户看，用户说 OK 才算定稿**；有问题就改，循环这个过程。

## 输入
- `task.md`：完整需求文档（drafting 阶段产出）

## 执行步骤

1. 阅读 `task.md`，对照模板（`workflows/requirements/templates/task-output.md`）自查结构：
   - `## 背景与目标`：背景/目标/成功指标是否明确
   - `## 范围`：范围内/范围外是否清晰
   - `## 功能需求`：每条 FR 是否三件套齐全、验收要点是否可测试
   - `## 验收标准`：是否为可测试的勾选清单
   - `## 待确认问题`：是否清零
2. （可选）如需机械确认结构，可运行：
   ```bash
   node .harness/workflows/requirements/check/req-check.js --task-id {task-id}
   ```
   它校验结构完整 + 待确认问题清零；失败项会列出。（非强制——需求文档以用户确认为准）
3. 把完整需求文档呈现给用户（gate: user_approval）：
   - **用户确认 OK** → 定稿（待确认问题必须已清零）
   - **用户提出修改** → 在本阶段内修改 task.md（改文档是简单编辑，不需要回退阶段）→ 再次呈现给用户确认 → **循环直到用户认可**
4. 定稿：用户确认 + 待确认问题为空 → 输出最终 `task.md`

## 输出
- `task.md`（定稿需求文档，**可直接作为 feature 流程的输入**）

## 约束
- **定稿的硬条件：用户明确确认 + 待确认问题区为空**
- 用户打回的修改意见，逐条落实后再次确认，不得"口头答应但文档没改"
- 不添加用户没提的需求（除非用户拍板）
- 定稿文档就是 feature 的 task.md——它的质量直接决定后续 designing/testing 的返工率
