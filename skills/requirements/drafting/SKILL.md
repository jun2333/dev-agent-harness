# Drafting Skill（需求文档撰写）

## 角色
需求文档撰写者。把"草稿 + 用户拍板后的答案"撰写成一份**完整、可执行、可验收**的需求文档。

## 输入
- `task.md`：需求草稿（elicitation 产出，含用户拍板结果）

## 执行步骤

1. 阅读 `task.md`，结合用户对待确认问题的拍板结果，确认需求已明确的部分
2. 按模板（`workflows/requirements/templates/task-output.md`）撰写完整需求文档：
   - `## 背景与目标`：明确背景、目标、成功指标
   - `## 范围`：范围内 / 范围外（防 scope creep）
   - `## 功能需求`：每条 FR 用三件套——
     ```markdown
     ### FR-1 {功能名}
     - 描述：{做什么}
     - 用户故事：作为{角色}，我希望{能力}，以便{价值}
     - 验收要点：{可验证的行为描述}
     ```
   - `## 非功能需求`（按需）：性能 / 安全 / 兼容 / 可用性
   - `## 约束`（按需）：技术栈 / 时间资源 / 依赖
   - `## 验收标准`：勾选清单（可测试的完成条件，喂给 feature 的 testing 阶段）
   - `## 待确认问题`：**还没拍板的继续保留**；已拍板的从清单移除
3. 功能需求拆解原则：
   - 粒度：一条 FR 对应一个可独立验收的能力
   - 验收要点必须"可测试"（避免"体验好""流畅"这类不可验证描述）
4. 识别需求间的依赖/冲突，在对应 FR 标题处显式标注（如 `### FR-2 ...（依赖 FR-1）`）

## 输出
- `task.md`（完整需求文档：三件套 FR + 验收标准 + 约束 + 剩余待确认问题）

## 约束
- 不臆造需求：草稿和拍板信息之外的内容，列为待确认问题而不是自行补充
- 验收标准必须可测试（喂给 feature testing 阶段的直接依据）
- 本阶段 gate 为 none（不打断）：文档是否合格由 review 阶段用户确认兜底
