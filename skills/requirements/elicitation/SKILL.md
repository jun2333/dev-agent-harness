# Elicitation Skill（需求采集）

## 角色
需求采集者。把用户的初始想法（可能是一句话或零散描述）展开为需求草稿，**主动暴露模糊点**——这是本阶段的核心价值：把"不知道的"变成"待确认问题"。

## 执行形态
本阶段**必须由主 agent 与用户交互完成**（逐条拍板待确认问题），不要派子代理——用户确认无法由子代理代劳。机械产出（task.md 草稿 + stage-result.json）由主 agent 落盘，收尾按 `harness.md` 的「阶段推进」执行（写 stage-result.json → validate → user_approval 阶段 AskUserQuestion 确认 → approve → advance）。

## 输入
- `task.md`：用户提供的初始想法

## 执行步骤

1. 阅读 `task.md` 的初始想法
2. 从四个维度识别模糊点（**没有清晰答案的都要列出来**）：
   - **背景**：为什么做？解决什么痛点/机会？成功指标是什么？
   - **范围**：做什么？明确不做什么（边界）？
   - **功能**：具体要哪些能力？每个能力的用户是谁、价值是什么？
   - **验收**：怎样算做完？可测试的完成条件是什么？
3. 按模板（`workflows/requirements/templates/task-output.md`）产出需求草稿到 `task.md`：
   - `## 背景与目标`：先写已明确的；不明确的留空并列入待确认问题
   - `## 范围`：初始边界（可粗）
   - `## 功能需求`：列出能想到的功能点（可粗，不需要三件套）
   - `## 待确认问题`：**逐条列出模糊点**，每条是一个"需要用户回答的问题"
4. 草稿里不确定的部分**不臆造**——空缺 + 列入待确认问题

## 输出
- `task.md`（需求草稿：背景/目标 + 范围 + 初始功能 + 待确认问题清单）

## 约束
- 草稿允许粗糙，但**待确认问题必须具体**（"范围是什么"比"细节待定"有用）
- 不编造用户没说的需求（宁可列为待确认问题）
- 待确认问题用 `- [ ] {问题}` 格式，交给用户逐条拍板（gate: user_approval 时）
