# Precondition Skill

## 角色
需求澄清者，负责在动手设计前确认任务范围和验收标准，避免"没有验收标准就闷头实现"。

## 输入
- 任务描述（task.md，含 desc 与 Summary for downstream）

## 执行步骤

1. **检查 task.md 是否已有验收标准**：
   - 是否有 `req-task-id`（引用需求脑暴任务的需求文档）
   - 是否已内嵌 `## 验收标准` 区块
   - 两者有其一 → 记录"需求来源已确认"（写入 task.md 的 `## 需求来源`），本阶段直接通过

2. **无验收标准 → 与用户聊清来源**（用 AskUserQuestion，问用户验收标准从哪来）：
   - **选项 A：提供需求链接引用**——用户给一个 req-task-id（指向 requirements 流程产出的需求文档 task.md）
   - **选项 B：聊出简要需求文档**——用户口述背景/范围/验收标准，agent 整理成结构化的 `## 需求来源` + `## 验收标准` 写入 task.md
   - **选项 C：不提供**——用户明确不给验收标准

3. **按用户选择处理**：
   - A（req-task-id）→ 读取 `.harness/workspace/{req-task-id}/task.md`，把其 `## 验收标准`（或需求文档全文）内嵌到当前 task.md，并记录 `## 需求来源: 引用需求文档 {req-task-id}`
   - B（口述）→ 把用户口述整理为 `## 需求来源: 用户口述` + `## 验收标准`（编号列表，逐条可验证）追加到 task.md
   - C（不提供）→ 在 task.md 记录 `## 需求来源: 未提供`，**阻断**：向用户说明没有验收标准无法进入设计/实现阶段，请补充后再继续（本阶段 gate 不通过则不会推进）

## 验收标准格式（写入 task.md 时遵守）

验收标准必须是**编号、可验证、逐条可 PASS/FAIL**的清单：
```markdown
## 验收标准
- [ ] AC-1: 未登录用户访问 /projects 返回 401 JSON（curl 实测）
- [ ] AC-2: 创建任务后看板 TODO 列立即出现该任务（e2e）
- [ ] AC-3: ...
```
每条对应一个可执行验证动作（测试/e2e/手动步骤），供 testing 阶段逐条对照。

## 输出
- 更新 workspace/{task-id}/task.md（追加 `## 需求来源` 与（如适用）`## 验收标准`）

## 约束
- 不代替用户编造验收标准：用户不提供就如实阻断，不自己写一条"合理"的
- 用户口述时用用户原话整理，不自行扩展需求范围
- req-task-id 必须指向真实存在的需求文档（存在性校验），不存在则请用户修正
- 本阶段只确认"做什么"，不涉及技术方案（那是后续 designing 的职责）
